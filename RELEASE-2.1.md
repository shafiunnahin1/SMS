# Release 2.1 — Exam Management Parity, Import and OMR

> **Status:** Draft proposal for later addition to `E:\Projects\School Management`. This file is a release plan, not an implementation report. No code has been changed in either project.
>
> **Purpose:** Bring the usable feature set of `E:\Projects\exam-management` into School Management without reducing question-authoring, question-paper, import, exam-result or OMR capabilities. Reuse its existing UI and workflows as the reference; polish them where that improves clarity, speed, accessibility or reliability.
>
> **Release ID is provisional.** Keep the existing R1–R7 roadmap intact until the School Management owner confirms where this release belongs in the dependency order. Do not claim a release date or effort estimate before the required spike and baseline measurements.

## 1. Release Outcome

At acceptance, School Management must provide the exam-management capabilities listed below through its own tenancy, authorization, data, API and React frontend. The source application's Laravel/Blade templates are a UI and behavior reference; they are not copied as the destination frontend. Existing School Management modules remain available and retain their behavior.

The release has four non-negotiable conditions:

1. Every supported source question format can be represented, validated and imported. An unknown or invalid record must be reported, never silently skipped.
2. A single large JSON import can contain many question types and thousands of questions; import is staged, resumable and does not require loading the full file into application memory.
3. PDF and JSON math content retains its LaTeX source through upload, parsing, editing, persistence, rendering and export.
4. Existing paper-generation and OMR workflows retain feature parity. OMR correctness must not regress, and uncertain scans must be reviewable rather than silently saved as correct.

## 2. Portal and Permission Ownership

| Portal | Included responsibilities | Explicit boundary |

| Super Admin | Maintain platform question-bank curriculum, question-format catalogue, pricing/free rules, quiz packages, Writer/Moderator accounts, writer earnings and withdrawal processing; platform-level reports | Central-host only; no routine access to institution marks or private student records |

| Institution Admin | Set up institution academic mappings, exams, routines and result publishing; oversee institution papers and OMR; review institution question-bank spending and teacher limits | Tenant-scoped; can review institutional use, not alter platform catalogue ownership or writer payouts |
| Teacher | Search and use permitted questions, build papers/sets, enter assigned marks, configure/print/scan/compare OMR, verify scan records within assigned institution/class/subject | Tenant- and assignment-scoped; cannot publish platform catalogue content or see another institution's records |

`content_writer` and `content_moderator` already appear in School Management's role design. This release makes their portals operationally distinct. They may use the same central authentication service, but must land on different dashboards and must not share privileged actions through a common page.

#### Advanced Editor Parity

The current School Management React editor and its D72/D73/D74 contract remain the layout and persistence baseline. This release expands authoring capability inside that layout; it must not replace the locked left-parts navigation, central editing surface/ribbon, right live preview, safe rich-content allowlist, metadata rail, or mobile editor/preview switch.

- Add source-equivalent metadata-driven authoring profiles and purpose-built controls for passage, choice, creative, short-answer, writing, primary-writing, transformation, identification, matching, information-transfer, substitution, problem-solving, visual-response, oral, practical and generic question families. Each profile provides type-appropriate labels, instructions, audience/word limits where applicable, given/required fields, expected result, marking rubric/criteria and answer guidance; do not send every type through one generic question/answer form.
- Preserve the source's type-specific builders and editor contracts for MCQ/choice groups, shared passage/stimulus with mixed child types, multi-part creative questions, gap/cloze (with and without clue), matching, sequence/rearranging, table completion/information transfer, writing and media-writing. Reuse School's existing D73 mixed child-item kinds (MCQ, written, gap, true/false with correction, table-fill, pair/triple matching, multi-field and ordering) rather than creating duplicate item models.
- Port source-supported interactive visual authoring tools, not just a JSON parser or read-only renderer: inventory all 32 registered QMX diagram modes and 27 graph types (including function, polar/parametric, statistical, vector-field and 3D-space graphs), and classify each with source evidence as editable, import-only, read-only/render-only or unsupported. Registry membership, successful import or visible rendering alone does not prove editability. Every source-editable mode requires create/edit/reopen/replace/delete, preview, media placement and dataset-linking parity as supported by its source contract; import-only and read-only modes retain their source behavior and must not be presented as editable. Keep visual schema/version contracts and field-level validation; unsupported modes must retain their staged source or produce a field-level report, never be silently flattened to an image.
- Maintain editor parity by task, not by copying Blade markup: context-aware controls, complete options/answer/marks, multi-row/group operations, per-part marks and source metadata; selection-preserving ribbon actions, undo/redo, rich-text formatting, math insertion, tables, image paste/drop/resize/position/rotation/transparency, live preview and draft/revision feedback.
- Every format and source-verified editable visual authoring mode must create, save, reopen, edit, preview and export round-trip fixtures in React. Import-only and read-only/render-only visual modes require their corresponding preservation or safe-render fixtures; they do not count as editor parity. A feature available only through import JSON, legacy Blade, or a read-only preview does not count as editor parity.

### 3.3 PDF Import

- Upload supported PDFs, select page ranges, create an import batch and extract selectable text, questions, metadata, images and math candidates where detectable.
- Support batch status, re-extraction when allowed, per-question review/edit/quick-edit, LaTeX review, validation, duplicate warnings, reject/discard and selected-question import.
- Preserve source page and import provenance so a reviewer can compare extracted content to the PDF.
- Detect scanned or hybrid PDFs. If OCR is not available, mark the batch/page as requiring OCR or manual handling; do not imply that unreadable pages were imported successfully.
- PDF-extracted questions remain staged drafts until reviewed and explicitly finalized/imported. No low-confidence extraction is auto-published.

### 3.4 JSON Import: All Formats and Large Batches

> **Implementation timing:** TOON import and its staged review/edit/save flow are recorded here for future implementation. This draft does not authorize application changes or activate the feature. Implementation may begin only after the owner approves the required locked decision and adds the work to the generated QB task plan and active release scope; until then, existing import behavior remains unchanged.

- Provide a versioned canonical question schema and downloadable JSON and TOON examples. Accept JSON files, multiple JSON files, pasted JSON, TOON files/payloads and large mixed-question batches. TOON (Token-Oriented Object Notation) is an additional School destination input format, not an Exam Management source-parity feature; both encodings must normalize to the same canonical question records and validation rules.
- The schema must represent every active question format and its relevant structure: question content, answer, explanation, options/correctness, marks, metadata, stimulus, creative parts, structured items, media references, source occurrences and supported visual specifications.
- A mixed batch may contain different supported question types; each record must declare its type and satisfy that type's contract. Unknown types or unsupported structures must be retained in staging with actionable errors, never silently flattened or discarded.
- Store mathematical content as LaTeX strings inside the JSON content nodes (question, option, answer, explanation, parts/items and stimulus as applicable). For TOON, preserve the equivalent decoded string values exactly. Parse valid JSON escapes correctly and preserve the exact decoded LaTeX source; do not apply lossy backslash repair to valid data.
- Validate schema version, question type, required fields, child structures, metadata references and media/visual contracts per record. Return clear per-record errors and warnings with source file, record index and field path. Malformed TOON syntax, unsupported TOON versions and invalid records must fail visibly without corrupting other accepted records.
- Use staged, chunked/queued processing with progress, retry/resume, idempotency, batch counters and a downloadable error report. A failed record must not invalidate already accepted records in another chunk; the batch must show partial success explicitly.
- Before finalizing questions into the question bank, provide a review table for all staged records with per-record selection, warnings/errors and a quick editor for correcting supported text/metadata fields. Quick edits update the staged record; they must not require opening the full editor. Finalize only selected, valid records as unpublished drafts. Unselected records must not be inserted into the question bank. After finalization, each saved draft must open in the existing full question editor and preserve its content on save/reopen.
- Detect possible duplicates and require explicit reviewer choice where confidence is insufficient. Never duplicate silently or overwrite existing questions.
- Import results enter the same staging/review/edit/finalize pipeline as PDF questions. JSON import must not bypass Writer/Moderator authorization or publication rules.
- Operational file-size and batch limits must be configurable and documented. Release load test: a mixed JSON batch and a mixed TOON batch of at least 10,000 valid questions each complete through chunked processing within the agreed environment budget, with exact counts, preserved LaTeX, actionable invalid-record reporting and no silent loss. Acceptance fixtures must also prove JSON/TOON equivalence for the same canonical questions, mixed-type parsing, per-record failures, selected-only finalization, staged quick-edit persistence, and full-editor save/reopen. If production hardware cannot meet this baseline, document measured capacity and obtain owner approval before lowering it.

### 3.6 OMR Forms, Scanning and Results

- Configure OMR form from a question set, including roll digits, option count/labels, question count, page size/orientation, columns, identity boxes, marks, negative marks and multiple-answer policy.
- Generate and print OMR forms; allow preview/layout adjustment before final generation and lock the generated form against accidental layout edits.
- Accept supported upload/camera or digital-entry scan workflows; retain scan source/image where permitted and keep a traceable scan record.
- Compare scans against the correct main/subset answer key; detect missing/invalid set codes, set mismatch, wrong answer count, invalid options and duplicate student scans.
- Provide fallback/cancel rules for an invalid set only through an explicit operator decision; identify class, roll, division/section, branch and subject before committing results.
- Support single and batch comparison, preview, record selection, manual identity confirmation, duplicate update/create resolution, per-record errors, verification, result review and batch save. Preserve the existing source batch capacity of up to 200 records unless a measured, tested increase is accepted.
- Calculate correct, incorrect and unanswered counts; marks, negative marks, total/percentage, pass conditions and grade using the configured key and policy. Persist OMR results only to the matching institution/session/class/subject/exam and student identity.
- OMR is an assessment input, not an automatic result publisher. A teacher/admin with the required assignment must verify and submit marks; an authorized institution admin publishes the final result.

### 3.8 Purchases, Wallets and Platform Operations

- **School Management payment and pricing design is authoritative. Do not port the source app's generic per-user wallet, personal top-up system, question-type subscription plans, included-unlock plans or subscription discounts.** These conflict with D47/D55/D66 and must not create a second payment/balance system.
- Preserve answer unlocks and purchase outcomes using School Management's `QbPricingService` (`qb_prices` + `qb_price_rules`) and `QbPurchaseService`. Keep D66's complete price-rule engine; do not add question-bank discount subscriptions. The server computes all prices; clients never submit amounts.
- Institution purchases use the existing shared institution taka wallet (`institutions.sms_balance`) and `sms_credit_transactions` with `type=qb_purchase`, through the existing `QbPurchaseService`. One purchase unlocks for that institution's teachers; a `private_batch` is a separate institution and buys separately. Do not add another institution wallet or write directly outside the canonical service/ledger.
- Student purchases and quiz-package orders use the existing School Management `QbStudentOrder` + `BkashService` flow: server-calculated amount/items, central-host callback, provider verification against order reference and exact amount, idempotent finalization, and existing `QbStudentController` unlock/package-access records. Students do not receive a generic wallet.
- Any SMS-wallet recharge must use the School Management's canonical D58 recharge/payment path. Keep D14's payment flows separate: question-bank student purchase is not parent fee collection and is not institution-to-platform SaaS subscription billing. Do not copy the Exam Management `PaymentService`, `PaymentGatewayManager`, dummy gateway or callback implementation into School Management.
- SaaS subscriptions remain governed by D47/D55: module-based pricing, no institution-size tiers or `max_*` limits, and platform subscription billing remains deferred as specified. This release must not activate, redesign or duplicate that billing flow.
- Super Admin credit/debit actions apply only to the canonical institution wallet using its existing adjustment/ledger path and audit rules. Preserve QB writer earnings, writer wallet ledger, held withdrawal requests and manual Super Admin payout with transaction reference as defined in School Management QB.10b; do not introduce automated disbursement.
- Financial cutover is a blocking reconciliation, not a wallet merge. Preserve source order/transaction references for audit; migrate verified paid question unlocks and unexpired quiz access into the corresponding target entitlement records when identity/item mapping is certain. Source personal wallet balances, pending payments and subscription-plan benefits must not be credited or converted automatically; classify each, obtain owner-approved settlement/conversion rules, and block cutover for unresolved money or paid rights.
- Keep all financial records append-only, exact-decimal, idempotent and auditable under D32/G9. Never infer a legacy balance or overwrite the School Management ledger.
- Preserve platform account administration and audit history; map legacy roles only after explicit review.

- Platform catalogue content (curriculum, questions, formats, concepts, resources, pricing) is platform-owned; institutional papers, exams, purchases, scans, attempts and results are tenant-scoped.
- Every tenant-bound read/write must use the current institution and fail closed. Cross-tenant papers, scans, wallets and results must not be addressable by changing an ID.
- Define a source-to-destination mapping for users/roles, institutions, academic sessions, classes/groups, students, subjects, question types, questions, media, revisions, sets/subsets, exam plans/routines/results, OMR forms/scans, purchases and ledger transactions.
- Migration must start with dry-run, counts, duplicate report and unresolved mapping report. It must support resumable batches and idempotent reruns; it must not delete or rewrite the source project.
- Reconcile source/destination counts, verified paid entitlements, payment orders and transaction history separately. Do not merge a source personal wallet into the institution wallet. Unresolved source balances, payment states or paid access rights block cutover until the owner approves a settlement/conversion policy. Retain source IDs as migration references for audit and support.
- Use School Management's canonical schema/API/module gates and current tenancy/security conventions. Do not introduce a parallel auth, tenant, student, wallet or payment system.
