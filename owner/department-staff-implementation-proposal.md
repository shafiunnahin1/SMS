## 1. Durable registration and activation state

**Recommendation:** add two narrowly scoped tenant-bound tables to R3.6a, in addition to its four planned department tables. Keep the existing User as the sole login identity. Reuse institutions.status=inactive for pending institutions and users.is_active=false for pending accounts; no new institution status enum value is needed. Do not change existing users or institutions automatically.

Draft columns below are proposed additions, not executed DDL. Every id is BIGINT UNSIGNED; every timestamp is nullable unless explicitly required. All tables have id primary key, institution_id NOT NULL FK, created_at NOT NULL, updated_at NULL.

| Proposed table | Proposed fields and constraints |
|---|---|
| institution_registrations | first_admin_id NOT NULL; source VARCHAR(20) NOT NULL (public/super_admin); review_status VARCHAR(20) NOT NULL (pending/approved/rejected); reviewed_by NULL; reviewed_at NULL; rejection_reason VARCHAR(255) NULL. UNIQUE(institution_id) ensures one first-principal registration. Composite FK (first_admin_id,institution_id) → users(id,institution_id). reviewed_by → users(id), verified in service to be an active central Super Admin; the platform actor deliberately has no tenant membership. |
| account_activation_requests | user_id NOT NULL; public_id CHAR(36) NOT NULL; purpose VARCHAR(30) NOT NULL (principal_activation/staff_activation/contact_change); generation INT UNSIGNED NOT NULL; channel VARCHAR(10) NOT NULL (phone/email); contact_hash CHAR(64) NOT NULL; otp_token_id NULL FK → otp_tokens(id); authorized_by NULL FK → users(id); status VARCHAR(20) NOT NULL (pending/verified/consumed/cancelled/expired); expires_at NOT NULL; contact_verified_at NULL; consumed_at NULL. Reuse the existing users composite tenant identity index. New schema uses append-only Laravel migrations after canonical approval; do not edit merged migrations or apply migrations to the shared demo DB. Department keys stay as already planned. Tenant export/purge/schema parity/query catalogs must cover the two additions; audit and financial history is never deleted by account provisioning.

One institution transaction lock plus the target user lock serializes provisioning, resend, verification, review and activation. Create first admin and registration atomically; reject any second first-principal request for that institution. A user may have several historical activation generations, but only the latest pending generation for that purpose can verify; issuing a replacement cancels its predecessor under the same lock. Validate OTP user, request user, purpose, current contact fingerprint, generation and tenant together; otp_token_id alone proves nothing.

Use an HMAC of normalized channel/contact with the existing application key for contact_hash; store the actual contact only on User. Never persist a raw activation secret. Bind OTP hashing purpose to activation purpose + request public_id + generation + channel + fingerprint; use the existing purpose-bound OtpService primitives with a transactional locked consume. This requires additive atomic-consumption coverage; current find-then-save consumption alone is not concurrency proof. Review/verification events contain IDs/state transitions, never contacts, passwords, OTPs or salary amounts.

Code expiry applies when consuming the pending verification challenge. Successfully recorded contact proof remains durable while its contact fingerprint matches; it does not lapse while a public registration waits for Super Admin review. Activation still rechecks current contact, explicit approval and account/request state; the old code can never be consumed again.

## 2. Onboarding, verification and recovery API

**Recommendation:** Super Admin provisioning itself records Super Admin approval, but neither its principal account nor institution becomes active before the principal verifies contact and sets their own password. Public verification records contact proof only; a subsequent explicit Super Admin approval activates both atomically. Rejected/pending registrations stay inactive. Generic institution toggle/update must not bypass this predicate for managed pending registrations.

Initial provisioning accepts exactly one login contact: contact={channel:phone|email,value:string}. Normalize using existing phone rules and the existing email/login comparison convention; no global contact uniqueness is introduced. Institution-local uniqueness, slug uniqueness/reserved slugs and validation remain. A secondary unverified login contact is not accepted in this first slice. Contact changes go through the principal, cancel outstanding challenges, revoke sessions and hold that managed account inactive until a newly authorized verification completes; manually deactivated accounts cannot reactivate using an old invitation.

Public registrants may choose their own password at signup under PolicyPassword; it is hashed and never returned. Super Admin/staff provisioning accepts no reusable password for the principal to see: create an undisclosed random placeholder hash, then require password+confirmation from the recipient on activation. Reuse password policy, hashing, token revocation and localized API error conventions. Existing ordinary reset/login behavior stays intact; inactive accounts use activation, not password reset.

| Endpoint (paths relative to /api/v1) | Recommended contract |
|---|---|
| Existing POST /super/institutions | Super Admin, central host only; name/slug/institution_type/admin.name/admin.contact; shared provisioning service, approval attributed to actor, pending verification. No client status/role/approval/module/subscription fields. |
| Planned POST /public/institutions | Central host; institution fields, principal name/contact/password+confirmation; transaction creates inactive tenant/account and pending review, no token or departments/duties. Return opaque registration/challenge tracking IDs and pending state, no secret. |
| Planned POST /public/institutions/{id}/verify | Central host; request public_id + code, and password+confirmation only for Super Admin-provisioned activation. Use the bound pending first-admin request, never arbitrary user_id. No tenant API token is issued here. |
| Planned POST /super/institutions/{id}/approve-registration | Central active Super Admin; body {decision:approve|reject,reason?}. Reject requires a reason. Approval requires current verified principal contact; identical decision retries are idempotent, conflicting review returns 409. No financial details in response. |
| Proposed POST /public/institutions/{id}/verification | Central host resend; tracking ID + matching normalized contact; always generic 202 for known/unknown submissions. No raw user/verification status disclosure; apply resend and attempt limits. |
| Planned POST /admin/staff | Active tenant principal only; display name + one contact; creates inactive institution_staff identity and sends activation. Return account ID/pending status, never password/secret. No department/duty/profile record is created implicitly. |
| Proposed POST /auth/activate | Unauthenticated endpoint on the correct active tenant host, for staff only; public_id/code/password+confirmation. Require matching principal-authorized latest activation. Principal signup verification remains on the central route above. |
| Proposed POST /admin/staff/{id}/activation | Principal-only resend/reissue for this tenant's pending staff; new generation, audit and generic response. Reactivation of a manually deactivated account requires explicit principal authorization, not merely a resend. |
| Planned PUT /admin/staff/{id} | Allowlisted account state/profile changes only; authorization assignment remains separate. New contact starts verification; deactivation atomically revokes sessions and pending invitations. |
| Planned PATCH /staff/profile | Own User.name/avatar only; multipart validated file rather than a client path. Reject role/is_active/contact/employee_id/HR/payroll/membership/duty fields. |

This proposes three additional R3.6a routes (17 → 20) and two tables (4 → 6), with no new task IDs or task reorder. The existing Super Admin endpoint is integration work, not a duplicate new route. These count changes need explicit owner approval and regeneration; they are not applied in this proposal.

Recommended initial limits, configurable and owner-reviewable: public creation 5 attempts/hour/IP; resend 1/minute per request and 5/hour per contact fingerprint; verification reuse existing 5/minute challenge/IP and five wrong-attempt invalidation; numeric OTP uses current configured five-minute expiry. No unlimited public retry, permanent contact lockout or real gateway configuration. Register a real signup limiter: the current provider has login/otp/api but no signup limiter. After-commit delivery must not leave an active account on delivery failure; resend recovers the pending request. No production SMS or real messages are sent during implementation tests.

Existing OtpService::sms prints codes into a local log, so that helper is not evidence of compliant activation delivery. Recommend a redacted activation transport using existing approved mail/SMS abstractions and in-memory fakes in tests: no raw activation secret in any application log or API response. Keep phone activation pending/fail closed when a safe configured transport is unavailable; do not silently mark it verified or substitute email-only behavior. Production exposure requires supported delivery for the chosen contact channel; this proposal configures no provider or real credentials.

## 3. Identity, profile ownership and legacy mapping

**Recommendation:** User.name/avatar are account display fields; email/phone/username, activation and permissions remain principal-controlled. Preserve existing StaffMember.name/photo as HR employment fields; do not silently overwrite them when account display fields change. Teacher/StaffMember designation, employee_id, joining/leaving dates, payroll/payee IDs and historical snapshots remain HR-owned. Department titles are display metadata and grant no access.

One existing User may link to one Teacher and one StaffMember profile if both already exist; this does not merge their payee IDs or financial history. No duplicate login/profile is automatically created. An account without either profile may still receive a non-HR department duty. Own teacher endpoints require the actual linked Teacher; any ambiguous/multiple same-type profile link fails closed and is listed for owner reconciliation. StaffMember.user_id may remain null until reviewed; legacy department strings never create memberships or permissions.

R3.6a adds foundation without auto-converting existing teacher/accountant accounts. R3.6b performs expand → report-only mapping → principal review → explicit per-tenant switch. Preserve previous role values for controlled rollback rather than dropping enum values. Before switching, require zero unresolved identity collisions and an explicitly reviewed per-user membership/duty mapping; no old role creates a default grant. Non-destructive rollback can restore the reviewed previous access model and revoke newly issued sessions; it never rewrites financial history or restores a revoked duty silently. No shared/live data backfill is authorized by this proposal.

## 4. Permission and resource-scope contract

**Recommendation:** use a code-owned registry of exact action keys and resource predicates; principal-defined duty names only group those keys. Unknown keys and wildcard grants are rejected. See `owner/department-staff-permission-proposal.json` for all 297 current runtime route entries. Every approval field remains null: this is a proposed matrix, not an applied catalog or proof of new enforcement.

| Actor/action | Recommended evaluation |
|---|---|
| Institution principal | Explicit principal authority for account/security/department administration; no department is needed to bootstrap the first department. All tenant/module checks, D33 impersonation denial and financial maker-checker rules still apply. |
| Department staff | Active same-tenant account + active non-archived department + effective active membership + active assigned duty + exact permission + resource predicate + existing module/feature gates. Never turn a department title or old teacher/accountant role into access. |
| Identity self-service | The seven own auth/session routes and three own-notification routes need active identity and owner checks, but no department duty. This permits logout/session cleanup without granting business access. |
| Shared programs/batches | Staff require explicit academic read permission; parent/student branches retain their existing behavior and data restrictions. These are business reads, not identity exceptions. |
| Academic attendance/results | Proposed staff permissions preserve actual linked-teacher/batch/subject assignment restrictions. A separate institution-wide academic scope is not granted by this proposal. Principal retains current authority. |
| Own teacher endpoints | Exact own linked Teacher/payee only, plus explicit duty; an HR-wide read permission never satisfies an own endpoint for another person. |
| Finance/HR/QB business actions | Separate exact action keys, tenant-bound records, existing append-only money, private resource serialization, purchase funding and maker-checker checks. A read duty grants no write/export/approval implicitly. |
| Student/parent/platform/public | Preserve their current branches and ownership/host/authentication checks. Do not apply staff duties to central callbacks or use platform roles to bypass D33. |

The matrix distinguishes delegable business actions currently limited to admin from principal-only identity/security controls. It does not assume that all 78 currently admin-only routes must remain principal-only. Conversely, an outer admin/accountant route is not proof that an accountant may approve: service restrictions win.

Dynamic actions are expanded, not granted as a blanket transition key: refunds approve/reject remain principal, process gets its own staff key; advances approve/reject/skip-installment/write-off remain principal, disburse gets its own staff key; leave approve/reject remain principal, staff cancellation is own pending only; imports dry-run/run/rollback have separate keys. Unknown selector values are denied. Report types are separately keyed from current ReportService allowlists (students/attendance/dues/fees; accountant dues/fees). Salary adjustment approval/cancellation, revision approval/rejection, bonus application and cashbook reopen retain existing principal/service constraints. Revision cancellation by a non-principal still requires that actor to be the preparer and retain existing state restrictions.

Do not spoof the actor's old role to satisfy services. R3.6b must replace role-based staff authorization branches with reviewed capabilities/resource predicates while keeping explicit principal approval checks and D33; add direct-service as well as HTTP tests. Until a route's new checks and tests are complete, it remains unavailable to institution_staff rather than inheriting legacy access. Register institution_staff in release/type/login/token policy only with foundation tests: recommended session lifetime 720 minutes absolute / 60 idle, matching the current accountant policy. It is a login identity across all four institution types, not an additional authorization grant.

No department templates or memberships are provisioned automatically. Duty revocation, membership end dates, account deactivation and department archive affect the next request without stale permission caches. Archive returns 409 while active memberships/duties remain; principal must revoke/resolve them explicitly. Existing financial/leave history is retained with its original actors; archiving never transfers or rewrites obligations. No new pending-department financial ownership is inferred where current rows have no such relation.
