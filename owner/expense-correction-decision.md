# Owner review: R3.1 expense correction contract

Proposal only; no implementation authorization until the owner approves the policy and commits its numbered row separately in `docs/LOCKED-DECISIONS.md` with the matching Change-Request trailer.

Evidence: R3.1 in `docs/AGENT-PLAN-R3.md` requires expense edit and soft deletion. D32 and guardrail G9 forbid financial-history modification/deletion; `.cursor/rules/database.mdc` permits soft deletes only for its listed tables, which do not include expenses. `docs/database/schema.sql` has neither `deleted_at` nor expense-reversal links. No Expense model/controller/migration/tests currently exist. `py -3.14 infra/spec-verify/plan_check.py .` passes 71 queries with zero problems.

Recommended policy: keep expense history append-only. The existing PUT and DELETE route contracts represent correction and cancellation rather than updating or deleting an expense row. A correction creates a negative reversal and a new positive replacement in one transaction; cancellation creates only a negative reversal. Signed monthly totals then retain the original spending history and reflect the correction without double counting.

Proposed schema additions for review: nullable `reversal_of_id` and `replaces_expense_id` self-reference fields on expenses, with tenant-bound validation and constraints preventing multiple reversals/replacements of the same expense. Nullable unique keys must allow many ordinary expenses with no reference; this requires an explicit exception to the generic optional-unique-key zero-default rule. The owner-approved schema must define exact FK/index names before a migration is written. These references serve ledger integrity, not a new product feature.

Manual creation accepts a positive exact decimal amount. Correction/cancellation operates only on an active manual expense in the current tenant, holds a row lock, rejects repeat correction/cancellation and system-generated payroll/advance/store/refund rows, and preserves all historical attachments and entries. Negative reversal amounts are computed on the server. Existing route auth/module/role gates and D32 audit requirements remain in force. Monthly reporting uses signed amounts with the existing institution/date index; no new table, route, UI, payroll, cashbook or wallet implementation is included.
