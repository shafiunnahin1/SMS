## Evidence and blockers

- R3.2 is accepted in progress and pushed as 75705a9; R3.3 is the next incomplete financial task. R2.1 execution remains after R3.A under D83.
- The generated R3.3 plan requires SubscriptionRefundTest to prove platform subscription refunds and term adjustment. Locked D55 defers platform subscription billing until all modules are built and module-based billing is specified. The older finance specification also asks to mutate payments.refunded_amount/refund_note/status. These historical instructions cannot silently override D55 or establish a new subscription policy.
- fee_refunds currently contains one mutable-looking request/status/actor snapshot without a request/revision identity. R3.3 requires refund rows immutable, and D32 protects financial history. Define the request/approval/processing history before implementing transitions.
- D82/current CashBookService counts positive fee receipts plus signed expenses. Negative fee reversal rows must restore dues without also becoming a second cash outflow. Cash refund processing must share the institution lock and cash-day validation already used by fee collection/expenses.
- No FeeRefundController, SuperRefundController or Refund test implementation was found in the inspected current application paths. Payment/SubscriptionInvoice models exist; their presence does not authorize deferred subscription behavior. No database was accessed for this audit.

## Proposed owner resolution

1. **R3.3 delivers institutional fee refunds only.** Preserve the five planned tenant fee-refund routes under fees and existing tenant/auth/role middleware. Defer subscription money/credit-note/term-adjustment execution and the planned SuperRefundController route to D55's future module-based billing refinement. Keep the future subscription requirement in the backlog; do not discard it or invent expiry/proration rules. Preserve the planned SubscriptionRefundTest name as a fail-closed deferral regression: the unimplemented subscription refund route remains unavailable and existing payment/invoice records are unchanged. This is an explicit proposed acceptance clarification, requiring owner approval before protected plan/spec changes; no existing tests are removed or weakened.
2. **Append-only fee refund lifecycle.** Extend fee_refunds with a UUID request_key and positive unsigned revision, unique per institution/request_key/revision; retain existing financial/status/actor fields as immutable snapshots. Revision 1 is requested; approval, rejection and processing append the next snapshot under the institution lock. The original request row ID remains the API identity; reject arbitrary revision IDs as request identities. Never update/delete a prior snapshot. A request's amounts/lines/method cannot be edited; a changed request is a separate request. Current state is its latest revision, and processed amounts are counted once per request, not once per snapshot. Existing approved tenant-purge behavior remains the sole deletion exception.
3. **Exact caps, identity and retry behavior.** Create accepts an explicit UUID request_key for tenant-local retry identity. Repeating the same key with the same canonical payload returns the original request; a different payload under that key is 409. Each line must refer to a positive, non-waived original fee payment for the same tenant/student/original receipt; no duplicate input line IDs or non-positive/excess/over-precision amounts. Use Money/paisa exact-decimal arithmetic. Check the processed net refundable balance at request and again at processing under the shared institution lock; pending requests do not reserve funds. An insufficient remaining balance is 422. Tenant-bound references/uniqueness must enforce the approved identity at DB and service boundaries.
4. **Roles and transitions.** Admin/accountant request and process; approval/rejection is admin-only. Requested → approved/rejected; approved → processed. Requesters cannot approve their own request, except an institution with exactly one active admin may use the documented single-admin exception with explicit audit evidence. Repeating an already-applied identical transition returns the existing result without duplicate revisions, reversal rows, expenses, receipts or SMS; conflicting/stale transitions are 409. Every successful transition has audit evidence. No teacher/student/parent or central user may use tenant refund actions without the existing tenant authorization contract.
5. **Processing transaction and cashbook.** Capture processing time once under the institution lock. Append negative fee_payments reversal rows with the same canonical student/enrollment/category/month, reverses_id pointing to original lines and a unique RFD receipt/line sequence. Originals never change. Append one positive refund expense for the payout, with source=refund and the actual payout method; this is the sole cashbook cash outflow for a cash payout. Use the processing date for both reversal timestamps and expense date. CashBookService::assertCashWrite checks the cash processing date; closed cash day is 409 day_closed. Do not backdate against the original receipt or reopen a day implicitly. All effects commit atomically; retries cannot double-count. Consent-aware transactional notification is dispatched after commit only once, and generated refund receipts retain original receipt references.
6. **Online branch stays fail-closed.** Online gateway/settlement refunds require the online_payment module and its approved contracts. With that module unavailable, reject online_payment_id/online_gateway processing explicitly; do not create online/settlement tables, invoke real gateways or port future R6 refund APIs. Offline cash/bank/bKash/Nagad payout recording uses the approved manual flow; it does not invoke a payment provider.
7. **Authorized follow-up if approved.** Permit only corresponding fee-refund schema/API/module/R3.3 scope/acceptance clarification, generated planning/export/query/purge artifacts and R3.3 backend implementation/tests. Preserve D32/D55/D81/D82, module lists, independent financial reference fixtures and task order. Required checks: RefundCapTest, RefundDueRecalcTest, RefundImmutabilityTest, RefundSettlementTest and the explicitly clarified SubscriptionRefundTest; shared CashBook/CrossTenant regressions, full backend/frontend/theme checks, refs_r11.py, plan freshness/schema parity/query-plan, deep verifier and staged guard. No UI task, application/demo DB migration, live gateway/payment, subscription implementation, R3.4 or R2.1 execution is authorized by this proposal.
