# D123 — draft for the owner (copy the row below into docs/LOCKED-DECISIONS.md right after the D122 row)

| D123 | R2.1.3 scope: JSON + TOON bulk question import through a staging review | Owner approved (2026-10-19). R2.1.3 may be built, after R2.1.2, with this refined scope; screens keep qbank's look and order (D110: upload page, then the staging table with quick edit, then "import selected"). (1) Formats: qbank's JSON (`exam-management.universal-content-json.v5`, as its `/ai-json/schema/download` example; an object or a bare array of questions; a file without `schema_version` is read as v5) and TOON (Token-Oriented Object Notation, spec v2.x) carrying the same records; both become the same canonical record. SMS publishes its own downloadable schema and one JSON and one TOON example. Unlike qbank, every type in `qb_question_types` (all Bangla and English types, structured items, passages, matching, gap-fill etc.) and both languages are accepted: a record names its type by slug or name (Bangla/English alias); an unknown type or a structure that type cannot hold stays in staging with an error - never silently turned into MCQ/short/creative. (2) Input: pasted text, one or several `.json`/`.toon`/`.txt` files; limits in config (default 20 MB per file, 10,000 questions per batch). TOON is decoded by SMS's own PHP decoder written to the public spec (no new package, G7 unchanged), with its own fixtures. (3) LaTeX: valid JSON/TOON strings are kept exactly as decoded - no backslash "repair" of valid data; a question with math is flagged for a LaTeX check in staging, not changed. Images are not uploaded by the import; `figure_descriptions` and qbank `visuals` (graph/diagram specs) are kept on the staged record, and graph/diagram tokens (D118) pass through unchanged. (4) Staging: two new platform tables (no institution_id, like the other `qb_` catalogue tables), `qb_import_batches` (uuid, format, schema version, file names + sha256, status, counters: total/valid/invalid/duplicate/imported, created_by) and `qb_import_records` (batch, file, record index, type, canonical payload JSON, field-path errors, warnings, LaTeX flag, duplicate status + matched question, selected, imported question id); added to schema.sql in the implementation commit. Parsing runs in queued chunks (500 records) with progress, resume after a failure and idempotency (re-running a chunk never doubles records; re-uploading the same file sha256 by the same person reopens the existing batch). Each error names the file, record index and field path; a bad record never blocks the others; the batch shows exact counts and an error report can be downloaded (CSV). (5) Review: a table of all staged records with select, filter by valid/invalid/duplicate, and qbank's quick edit for text and metadata (type, class, subject, chapter, topic, marks, difficulty, language) plus bulk settings for the selected rows; edits change only the staged record. (6) Finalize: only selected, valid records become questions, always as DRAFT owned by the importing writer, through the same rules as the editor (no publishing from the import); then they open and save in the full editor as usual. Duplicates: same normalized text + subject + type as an existing question is marked "possible duplicate" and needs an explicit choice per record (skip or import anyway); never silent, never overwrite. (7) Roles: content writers and the Super Admin import; moderators review the resulting drafts as usual; a writer sees only their own batches, the Super Admin all. (8) Acceptance: a mixed 10,000-question JSON batch and the same questions as TOON both finish through chunks with exact counts, identical canonical records (JSON/TOON equivalence), unchanged LaTeX, per-record failures, selected-only finalize, quick-edit persistence and full-editor save/reopen; measured time is recorded in PROGRESS. Implementation commits carry `Change-Request: D123`; the R2.1 guard map gains `R2.1.3 -> D123` and `R21_TABLES` the two tables, in a separate guard commit merged to main first (as D122). |
