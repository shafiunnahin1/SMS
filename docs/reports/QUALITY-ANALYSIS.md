## ২. শক্তির জায়গা (প্রমাণসহ)
1. **একক সত্য-উৎস ও অগ্রাধিকার:** `AGENTS.md`-এ ২৪টি Locked Decision, "কোন ফাইল জেতে" ক্রম, Owner Actions, Open Decisions। অনেক প্ল্যানে এটিই থাকে না।
2. **Tenant বিচ্ছিন্নতা বাস্তব-ঝুঁকি ধরে নকশা করা:** তিন mode (`tenant` / `:central` / `:optional`), `EnsureUserBelongsToTenant`, `RoleMiddleware`-এ host-বনাম-role দেয়াল, suspended-প্রতিষ্ঠানের জন্য সীমিত পথ। audit পাসে এখানেই সবচেয়ে গুরুতর ফাঁক ধরা পড়েছিল ও সারানো হয়েছে।
3. **টাকার প্রবাহ সতর্কভাবে:** server-computed amount, row-locked idempotent `finalize`, mode-স্থিরতা, `review` অবস্থা (টাকা কাটলে কখনো `failed` নয়), settlement ledger, দায়ের আলাদা রিপোর্ট।
4. **Extensibility seam:** gateway registry, VARCHAR কলাম, flow-aware interface, theme token/layout registry, `config/institution_types.php` — নতুন gateway/layout/type যোগ করতে code-এর একাধিক জায়গা বদলাতে হয় না। `RegistryExtensibilityTest` এটি প্রমাণ করার জন্য পরিকল্পিত।
5. **যাচাইযোগ্য ধাপ:** প্রতিটি Step-এ Spec Reference, Tests, Done When; ৮০+ নামযুক্ত test।
6. **সততা:** যাচাই-না-হওয়া তথ্য (gateway URL, masking ID নিয়ম, আইনি প্রশ্ন) চিহ্নিত; স্থানধারক `TODO` আলাদা করে দেখানো।

### 🟠 M1. Controller-স্তরে নির্দিষ্টকরণ পাতলা
- routes-এ ৬০টি controller, প্ল্যানে **৫টির** class body আছে। বাকিগুলো `Controller → FormRequest → Service → Resource` প্যাটার্ন + endpoint-টেবিল থেকে অনুমেয়। Service-স্তরে (Fee, Enrollment, Payments, Result) গভীরতা ভালো; এটি যুক্তিসংগত, কিন্তু validation নিয়ম, response আকার ও error কোড অনেক জায়গায় অনির্দিষ্ট।
- নামযুক্ত test নেই এমন মডিউল-কী প্রায় অর্ধেকের বেশি (কীওয়ার্ড-ভিত্তিক মাপ; আনুমানিক): `behavior, certificates, cpd, events, scholarships, visitors, alumni, parent_meeting, online_class, online_quiz, hostel, transport, hr_payroll, multi_branch, gps, ai_assistant …`। Phase 7-এর "Done When" সাধারণ ("spec-এর endpoint ও page কাজ করে")।

### 🟠 M2. Tenant scope **fail-open**
`BelongsToInstitution` global scope শুধু `currentInstitution` বাঁধা থাকলে filter করে; না থাকলে **কোনো filter ছাড়াই সব প্রতিষ্ঠানের ডেটা** ফেরত দেয়। আজ route-mode, queue-job-এ হাতে-bind নিয়ম (AGENTS rule 8) ও test এটি আটকায় — কিন্তু একটি ভুলে-ছাড়া bind, একটি ভুল `optional` route, একটি নতুন console command সবকিছু ফাঁস করবে। এটি নকশা-স্তরের ঝুঁকি, মানবিক সতর্কতার উপর দাঁড়ানো।
**সমাধান:** fail-closed — bind না থাকলে exception; যেসব জায়গায় ইচ্ছাকৃতভাবে সব-tenant দরকার (Super Admin, scheduler) সেখানে স্পষ্ট `Model::withoutTenancy(fn)`। `TenantIsolationTest` তখন এই ফাঁদ নিজেই ধরে।

### 🟠 M3. নমুনা কোড যাচাই-না-করা
- PHP/JSX কোনোটিই compile বা চালানো হয়নি; শুধু bracket-balance স্ক্রিপ্ট। আগের audit-এ আমার নিজের কোডেই অসংজ্ঞায়িত ভেরিয়েবল (`$activeStudents`), ভুল `proxy_pass`, ভুল unique key ধরা পড়েছিল — অনুরূপ ত্রুটি যে আরও আছে তা ধরে নেওয়াই যুক্তিসংগত।
- "Done When" ও test এই ঝুঁকি ধরবে, কিন্তু প্ল্যান-পর্যায়ে নয়, নির্মাণ-পর্যায়ে।

## কী বদলাল
আগের ধাপগুলোর রেটিং ছিল নথি পড়ে ও regex-স্ক্রিপ্ট চালিয়ে। এবার প্রথমবার **স্কিমা সত্যিই execute** করা হয়েছে, ৩০টি আচরণ-পরীক্ষা চালানো হয়েছে, ৭২টি কোড-ব্লক parser-এ দেওয়া হয়েছে, আর পুরো যাচাই এক কমান্ডে (`infra/spec-verify/verify.py`) ফেরানো যায়, ১৪ ধরনের ইচ্ছাকৃত ত্রুটি ঢুকিয়ে যার সংবেদনশীলতা প্রমাণিত। ফলে **আগের "সামঞ্জস্য ঠিক আছে" দাবি অতিরঞ্জিত ছিল**: ১১টি বাস্তব ত্রুটি বেরিয়েছে (দুটি 🔴: MySQL-এ migration ভাঙত, ফি-নির্ধারণ বছর দেখত না), এবং আমার নিজের দুটি যাচাই-সরঞ্জামও ত্রুটিপূর্ণ ছিল।

## সৎ সারাংশ
প্ল্যান এখন আগের চেয়ে **অনেক বেশি যন্ত্র-যাচাই করা** ও নিজের সাথে সংগত। কিন্তু এটি এখনো একটি স্পেসিফিকেশন: কোনো কোড, কোনো পরীক্ষা, কোনো ব্যবহারকারী, কোনো সময়-মাপ নেই। যত ফিচার যোগ হয় ততই **Spike-গেটের আগে আর কিছু লেখা ঝুঁকিপূর্ণ**; আমার সুপারিশ — বাকি ৭টি স্পেক (ক্যাশবুক/refund প্রথমে) লিখে Spike-এ যাওয়া, আর P-তালিকা থেকে শুধু সস্তা Tier-A গুলো।
